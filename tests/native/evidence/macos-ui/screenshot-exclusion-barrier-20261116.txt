macOS exclusion-based screenshot coordination, 2026-11-16

The change addresses an ordering gap: an asynchronous exclusion-based area or
scroll screenshot could begin with one set of window IDs while a newly registered
daemon overlay was still hidden, then the overlay could become visible before
the screenshot completed. The screenshot now includes registered daemon-window
IDs from its initial snapshot. Recording outlines, dim overlays and camera
panels wait for screenshots already in flight before they become visible.

The existing native scroll fixture adds a synthetic actor-coordination case:
one screenshot begins with ID 61; ID 62 is registered; a second screenshot sees
both IDs; a pending presentation waits for both. A third screenshot begins
before the presentation continuation runs, and the presentation waits again.
The case passed along with the existing scroll and recording-coordination tests.
The opt-in ScreenCaptureKit pixel check was skipped, and no screen or device
capture was started.

This is an ordering test, not captured-pixel proof. The legacy direct screenshot
path is not covered, and AppKit tooltip windows are not registered by this
change. A registered window removed during a strict capture can make that
capture fail closed; live screen, scroll and recording tests remain necessary.
